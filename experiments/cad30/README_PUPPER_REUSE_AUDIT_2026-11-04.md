# Hexapod Lab — аудит готовых контроллеров четвероногой походки

**4 ноября 2026. Результат: Stanford Pupper выбран как первый готовый источник алгоритмов походки, но реальная четырехногая ходьба CAD30 пока НЕ подтверждена.**

## Зачем изменили курс

Проект #21/#26/#36 пытался «вытолкнуть» конкретную четырёхопорную позу B через многозвенную предиктивную оптимизацию. Полученная статическая цепочка из 69 контрольных поз в MuJoCo физически остановилась ещё в подготовке (0/69 реально пройденных узлов). Проверяем архитектуру на основе готового четвероногого gait-controller вместо разработки нового MPC/ИК.

## Обзор готовых решений

| Проект | Совместимость с задачей | Итог |
| --- | --- | --- |

Оригинальный контроллер рассчитан на четвероногое шасси, а стандартная матрица `contact_phases` — **диагональная походка с двумя одновременными swing**, не медленный crawl. Проект Pupper v1 больше не поддерживается. | **Основной источник простых проверяемых блоков**: переиспользовать scheduler, stance/swing-парадигму и только конфигурировать 4-тактный режим. |
| [CHAMP](https://github.com/chvmp/champ) | BSD-3-Clause; популярный робототехнический стек, настройка геометрии и смещения центра масс. Требует ROS/адаптации ROS2 и совместимого интерфейса; его типовой диагональный gait не означает три опоры в статическом режиме. | **Запасной** вариант для ROS-интеграции; сейчас не переносить всю инфраструктуру. |

| MuJoCo MPC / сложные torque-WBC | Готовые пакеты есть, но основаны на иной аппаратной модели и предполагают серьёзную настройку задач и контактов. | Пока не нужны для доказательства базовой медленной crawl-походки. |

## Выполненный реальный тест совместимости

- Исходная геометрия: наша CAD30 Freenove FNK0052 с 30 локально восстановленными CAD-мешами, MuJoCo 3.14.0, масса **1.8048682 кг**.
- Сохранённое физически просчитанное состояние `cad30_safe_pose_B_nominal.json` из исследовательского PR #34 (восстановить отдельно с Google Drive/из research-ветки). 4 реально контактирующие опоры `ml/mr/bl/br`, передние `fl/fr` подняты; проекция COM `(0.000104543, -0.015270450)` метра в плоскости пола.
- Сопоставление ног: Pupper `front_left`→`ml`, `front_right`→`mr`, `hind_left`→`bl`, `hind_right`→`br`. «Передняя» пара в этом сопоставлении — **средние ноги шестиногого**; исходные передние `fl/fr` остаются манипуляторами.
- **Оригинальный GaitController использован без правки алгоритма**. Адаптирована только конфигурация `SlowCrawlConfig`: 8 фаз = 4 четыре-опорных паузы + 4 периода swing ровно одной ноги. Условный порядок `bl → mr → br → ml`. На 800 проверенных тактах scheduler никогда не требует меньше 3 опор, каждая нога поднимается ровно один раз за цикл.
- Реальные контактные точки взяты из `mj_forward` на сохранённой позе, а не придуманы. Запас устойчивости COM в исходной конфигурации при выключении выбранной стопы:

| Поднятая нога | Signed static support margin, мм | Успешен без дополнительного смещения корпуса (порог +5 мм)? |
| --- | ---: | --- |
| `bl` | +16.19374 | Да, **геометрически** |
| `br` | +16.19374 | Да, **геометрически** |
| `ml` | −96.53695 | **Нет** |
| `mr` | −96.63399 | **Нет** |

**Диагноз:** готовый scheduler работает и умеет один swing одновременно; но из текущей позы B медленная четырехногая crawl-походка статически невозможна **без подготовки/переноса COM перед подъемом средней ноги**. Это не дефект Pupper/CHAMP/Mink: геометрия и расположение COM проекта требуют иной исходной четырехопорной стойки, стабилизирующего переноса веса или временной помощи передними ногами. Не стоит «чинить» gait-controller добавлением сотен контрольных поз.

### Воспроизводимость

Из локального восстановленного проекта с установленными Python 3.13, NumPy, SciPy и MuJoCo 3.14.0:

```bash
python -m unittest -v test_audit_pupper_crawl.py
python audit_pupper_crawl.py \
  --model /path/to/source/mjcf/scene_local30_nominal.xml \
  --pose /path/to/cad30_safe_pose_B_nominal.json \
  --out results/pupper_cad30_scheduler_audit_2026-11-04.json
```

**Фактически выполнено локально:** 5/5 тестов PASS, из них один на восстановленной CAD30 сцене, четыре тестируют настоящий upstream scheduler (8 фаз, два оборота, порядок, некорректный конфиг). Без CAD реальный интеграционный тест должен SKIP, а не называться успешным. Полные числа и предостережения в `results/pupper_cad30_scheduler_audit_2026-11-04.json`.

## Что делаем после аудита (никакой новой тяжёлой архитектуры)

1. **Сначала геометрия, а не код:** найти из шестиногого старта четырёхопорную стойку, из которой стандартная crawl-походка с переносом веса может последовательно поднять все четыре ноги при ±1.7 рад как *исследовательском*, не аппаратном лимите. Если это не удаётся, измерять реальную массу и изменять расположение корпуса/батареи/точек стоп; возможно разрешить передним ногам кратковременный контакт при подготовке.
2. Использовать **существующие** Pupper `StanceController`/`SwingLegController` и совместимый Mink для 12 ходильных суставов. Минимальный адаптер только между world frames CAD30, body-relative ногами Pupper и приводами MuJoCo. Не переносить его массо-инерционные коэффициенты, servo PWM, URDF или конкретные длины звеньев.
3. Запустить один **стандартный** медленный crawl-цикл с контактом 3 или 4 настоящих опор; результаты считать от исходного шестиногого состояния, не скрывая подготовительную фазу. Проверять MuJoCo с dt=0.002, контакты/силы, фиксированные на земле опорные стопы, ограничения моментов, отсутствие падения/скольжения и положительное полезное продвижение корпуса, затем несколько циклов.
4. Только после устойчивой базовой походки сравнивать с Walknet и с реакцией на потерю опоры. Не создавать собственные IK/MPC и не реанимировать траекторию PR #36 как эталон.

**Статус:** аудит и геометрический тест прошли; интегрированный Pupper->Mink->MuJoCo контроллер ещё НЕ запущен, физической четырехногой ходьбы нет. Сохранять в draft PR; `main` не менять и не сливать без согласия; физические расчёты — не в GitHub Actions.
