# Replay Pipeline — опыт → Android-плеер

**Первый этап:** одна команда запускает физическую симуляцию, экспортирует уже
рассчитанные состояния, создаёт страницу с совместимым 3D-рендерером,
проверяет данные и добавляет новую неизменяемую запись в библиотеку. Опционально
публикует её в owner-managed ветке GitHub. Сам Android **не** рассчитывает физику.

## Использование

~~~bash
python scripts/replay_pipeline.py run experiments/replay-pipeline/EXPERIMENT.yaml --publish
~~~

Без флага --publish выполняются оба этапа и собирается локальный каталог.
Если настоящая симуляция уже просчитана, используйте --skip-execution:
проверка исходной трассы остаётся обязательной. JSON-спецификации работают
на Python stdlib; для YAML нужно установить PyYAML.

Ниже **шаблон**, а не готовый опыт. Замените имена двух команд-заглушек на
настоящие экспериментальные программы и экспортёр выбранного робота.

~~~yaml
schema: hexapod-replay-job/v1
id: wheelbot-next-001
title: "Mini Wheelbot · новый опыт"
detail: "10 секунд · MuJoCo · проверка самоподъёма"
robot: Mini Wheelbot
engine: MuJoCo
status: research
duration_s: 10.0
commands:
  simulate: ["python", "scripts/<real-simulator>", "--out", "results/wheelbot-next-001.json"]
  export: ["python", "scripts/<real-exporter>", "--trace", "results/wheelbot-next-001.json", "--out", "docs/hexapod/data/wheelbot-next-001.json"]
trace:
  path: results/wheelbot-next-001.json
  samples_field: samples
  time_field: t
  qpos_field: qpos
replay:
  path: hexapod/data/wheelbot-next-001.json
  format: mini-wheelbot-mujoco-physical-replay-v1
  trace_sha256_field: trace_sha256
  frames_field: frames
player:
  template: wheelbot-self-righting-v1
~~~

Требования к сырой трассе: JSON-объект с массивом samples, действительными
числовыми qpos и строго возрастающими отметками времени. Продолжительность
трассы должна соответствовать метаданным опыта (допуск 15% или 0,15 с).
Симулятор обязан сохранять настоящие состояния во время своих физических
шагов (для MuJoCo — mj_step). Для научных результатов также сохраняются
qvel, силы/контакты, параметры модели и входные воздействия.

Экспортёр должен создать массив настоящих физических кадров frames и
положить в указанный JSON SHA-256 **точных байтов** сырой трассы (вложенное
поле поддерживается, например source.trace_sha256). Совпадение SHA не
доказывает физическую достоверность само по себе: достоверность обеспечивает
проверяемый код расчёта и отдельные тесты модели.

## Шаги pipeline

1. Запустить simulate, затем export. Любая ошибка останавливает обработку.
2. Проверить qpos/время, версию формата, длительность, кадры и SHA-256 трассы.
3. Скопировать HTML/JS/CSS из существующего renderer-template в новый
   маршрут, заменив его ID на новый ID. Дополнительные точные замены могут
   задаваться в player.replacements.
4. Проверить ссылку на новый JSON, размеры и хэши файлов и передать запись
   в существующий scripts/register_viewer_replays.py. Повтор без изменений
   не повышает revision и не перезаписывает старые записи.
5. По --publish убедиться, что Git checkout стоит именно на ветке
   feature/android-local-offline-viewer-20261104, что нет лишних staged
   изменений и что origin — ожидаемый GitHub repo. Commit/push только
   созданных assets и library.json. main остаётся нетронутым.

Этот код сначала находится в **отдельном draft PR**. Публикация на
рабочую ветку возможна только после принятия PR в ветку плеера.

Сырые трассы и большие исходные данные архивируются на Google Drive по
принятым правилам проекта. GitHub хранит только код, отчёты, метаданные
и разрешённые небольшие HTML/JS/JSON. Сторонние STL/OBJ и секреты не
перезаливаются.

После публикации Android-плеер использует существующую кнопку
«Обновить библиотеку». Нет нового фонового демона, отдельного сервера
или обязательного запуска GitHub Actions для каждого опыта.

## Ограничения

- Пока нужны совместимые renderer-template и экспортёр для конкретного
  типа робота. Произвольный URDF/MJCF автоматически не визуализируется.
- HTML/JS создаются копированием проверенного шаблона; единый renderer для
  всех типов роботов — следующий этап.
- Статус passed/failed/research предоставляется экспериментом, а не
  вычисляется универсальным скриптом. Для автоматического статуса нужны
  отдельные физические acceptance-gates.
- Автоматического старта по GitHub Issue и загрузки исходников в Drive
  пока нет: агент должен вызвать эту команду внутри текущего исследования.

## Тесты

~~~bash
python -m unittest discover -s tests -p 'test_replay_pipeline.py' -v
~~~

Проверяются создание записи, идемпотентность, неизменяемость, фальшивый хэш,
отсутствующая или испорченная трасса, нарушенное время, NaN в qpos, ошибка
шаблона, небезопасные пути и защита Git-ветки.
