# Hexapod Lab — динамический каталог симуляций

Библиотека на планшете показывает **отдельную запись для каждого физического эксперимента MuJoCo**. Интерфейс запускает воспроизведение автоматически, зацикливает запись и использует оригинальные CAD-сетки Freenove (локальный кэш на планшете).

## Где хранится список

- \`docs/hexapod/library.json\` в **ветке \`feature/android-local-offline-viewer-20261104\`** — каталог, который проверяет кнопка «Обновить библиотеку».
- Реальные файлы HTML/JS/CSS/JSON, относящиеся к новой симуляции, размещаются в \`docs/hexapod/\`. Отправлять в GitHub STL не надо: при установке 30 оригинальных CAD-сеток уже кэшируются локально и сверяются по SHA-256.
- Сервер принимает только явно перечисленные в каталоге новые файлы, проверяет их размер и SHA-256, сохраняет локально и **лишь затем** обновляет список. В отсутствие сети прежние записи остаются работоспособными.

## Формат новой записи

Увеличить \`revision\` и добавить запись в \`entries\`:

\`\`\`json
{
  "id": "tripod-slippery-001",
  "title": "Tripod · скользкий пол",
  "detail": "Серия экспериментов с уменьшенным трением · 12 с",
  "duration_s": 12,
  "href": "/hexapod/tripod-slippery-001/",
  "files": [
    {"path":"hexapod/tripod-slippery-001/index.html","sha256":"<64-hex>","size":1234},
    {"path":"hexapod/tripod-slippery-001/app.js","sha256":"<64-hex>","size":5678},
    {"path":"hexapod/data/tripod-slippery-001.json","sha256":"<64-hex>","size":9012}
  ]
}
\`\`\`

Публикуются **все зависимости** новой симуляции; \`sha256\` и \`size\` относятся к полным оригинальным байтам каждого файла в GitHub. Сначала коммитить файлы, затем их манифест в том же коммите (или последующим коммитом). Физическая запись должна происходить из MuJoCo, не из постановочной JavaScript-анимации.

Каждый путь неизменяем: при необходимости исправить запись, используй новую версию и новый путь. Изменение уже сохранённого файла с другим SHA-256 блокируется, поэтому старые результаты не подменяются незаметно. Не добавлять файлы из сторонних доменов, бинарные STL или материалы с неясной лицензией.

Кнопка вызывает \`POST /api/refresh\` только на локальном Python-сервере. Сервер получает текущий commit SHA разрешённой ветки GitHub и скачивает версии файлов, закреплённые этим SHA. Скрытых фоновых опросов нет. Новый статус и список возвращаются прямо в браузер.

**Ограничения:** интерфейс показывает replay, не рассчитывает физику в браузере; масштабируемая синхронизация новых симуляций требует, чтобы Альфред публиковал каждую запись в совместимом формате. Если каталог содержит ошибку или ресурсы недоступны, обновление отменяется, а ранее установленная библиотека остаётся доступной.


## Обязательное правило: физический эксперимент → запись в локальном плеере

С 2026-11-04 любой завершённый новый MuJoCo-эксперимент (включая **отрицательный результат**) должен включать этап публикации в библиотеку локального плеера. Вызов входит **в тот же рабочий процесс**, который создаёт эксперимент и его PR; кнопка обновления на планшете только забирает опубликованные файлы. Это **не фоновый демон**, не GitHub Actions-вычислитель и не автоматическое сканирование всех репозиториев/PR.

1. **Протокол физики.** На исходной модели, в том же `mj_step` loop сохранять подлинные `qpos`, времена, имена фактически несущих ног и `Fz`; проверять переходы на каждом физическом шаге (например, 2 мс). Для плавного браузерного replay достаточно записанных 20–25 Гц поз с фактическими контактами, наблюдёнными в соответствующие моменты. Нельзя подменять отсутствующие `qpos` искусственной анимацией.
2. **Экспорт.** Из оригинальной CAD30-сцены и сохранённых `qpos` получать `fnk0052-physical-points-v1` (с реальным контактным битовым маскировочным словом) и `fnk0052-mujoco-cad-visual-replay-v1` (через `mj_forward`), записывать источник, хэши, длительность, статус и ограничения. Не коммитить Freenove STL/MJCF оригиналы или секреты.
3. **Каталог.** Для каждой реальной записи создавать новый неизменяемый id/маршрут `/hexapod/<id>/`, страницу и все JSON/JS-зависимости; отдельно маркировать `failed`/диагностику, если походка не получена. Новую запись *нельзя* назвать успешной походкой без фактических liftoff/touchdown и оценки перемещения. Рассчитать `size` и `sha256` по точным байтам.
4. **Автоматическая проверка записи.** Запускать `scripts/register_viewer_replays.py` из корня репозитория, указывая каталог, manifest записей и папку `docs/`. Скрипт проверяет путь, неизменяемость, SHA-256/размер, дубли, сохраняет старые записи и повышает `revision` **только при появлении новых записей**. Идемпотентный повтор ничего не меняет. Он **не** публикует код в GitHub самостоятельно.
5. **Публикация и приёмка.** Только после проверки и реального replay одновременно коммитить физические assets, страницы и `docs/hexapod/library.json` в ветку `feature/android-local-offline-viewer-20261104`; оставлять draft PR, `main` не менять и не merge без согласования владельца. На локальном планшете пользователь нажимает «Обновить библиотеку». Удостовериться, что manifest действительно доступен по указанной ветке; успешный GitHub commit сам по себе ещё не подтверждает Android WebGL.
6. **Сырые доказательства.** Полные записи `qpos/qvel`, 2-мс контактные трассы, код, исходную фиксированную модель/версию и контрольные суммы сохранять в приватный Google Drive. Код/компактные отчёты — GitHub. Ссылки на полный ZIP указывать в PR/Issue.

Пример локальной регистрации (каталог обновляется только в заданном выходном файле, не в `main`):

```bash
python scripts/register_viewer_replays.py \
  --catalog docs/hexapod/library.json \
  --entries /path/to/new_entries.json \
  --docs docs \
  --output /tmp/verified-library.json
```

**Эталон выполнения:** [CAD30 2/3/4-support PR #35](https://github.com/Dmitry-dev-pet/alfred-hexapod-lab/pull/35) — 9 × 2,4 с подлинной MuJoCo-динамики, заново записанные `qpos` (49 кадров на запись) и контактные реакции; 6 попыток получить 2 нагруженные ноги не достигли цели. Все девять физически воспроизведённых результатов экспортированы как отдельные записи каталога revision 3. Общий исследовательский replay-архив без сторонних CAD: [Google Drive](https://drive.google.com/file/d/1a8NIYvtCDtXgVqT9lfvxPetA2uRemeii/view), SHA-256 `6f51d380852691e06c9d02e7b2756a58443391c12d6d3471025ddc2618e92ad7`.


## Физическая запись из другого симулятора: Mini Cheetah / Drake

С 2026-11-04 тот же каталог может содержать **внешние эталонные физические симуляции**, не только MuJoCo/Freenove, если подтверждены настоящие состояния и контакты. Для каждой записи обязательны имя робота, физический движок, источник, версия, измеренная длительность, ограничения и ясная маркировка, что это другой робот. Нельзя выдавать движение внешнего робота за работу нашей CAD30.

Эталон: `cheetah-idto-10s` — нативная 10-секундная MPC-симуляция Mini Cheetah в Drake, данные: 201 измеренный кадр с реальными силами четырёх опор каждые 50 мс, цель за горизонт 0,4 м, итоговое поступательное перемещение около 3,467 м. 171/201 отсчётов имеют две несущие ноги при пороге 0,2 Н. Внешняя модель отображается **схематическим скелетом**, кинематика восстанавливается из исходного URDF и реальных записанных `qpos`. Оригинальные OBJ-меши в библиотеку не копируются.

В отличие от CAD30 это эксперимент в **Drake / TRI IDTO**, исходные физические данные и provenance описаны в [PR #33](https://github.com/Dmitry-dev-pet/alfred-hexapod-lab/pull/33). Код преобразования: `scripts/export_idto_cheetah_viewer.py` и тесты `tests/test_idto_cheetah_viewer.py`. JSON/HTML/JS опубликованы через revision 4 каталога. Локальные версии `player-shell.js` из старых установок могут ещё отображать общую надпись «MUJOCO · REPLAY», но заголовок конкретной страницы и сами данные ясно помечены как Drake; изменение общего UI требует отдельного обновления интерфейса, не только библиотеки.


## Единый конвейер для новых экспериментов

Начиная с новой реализации публикации использовать
[REPLAY_PIPELINE.md](REPLAY_PIPELINE.md): одна команда объединяет
запуск эксперимента, экспорт, проверку физической трассы, подготовку
страницы и регистрацию в этом же каталоге. Существующий
register_viewer_replays.py и локальный протокол Android-синхронизации
сохраняются без изменений. Для нового типа робота нужен адаптер
физического экспорта и совместимый шаблон отображения. Пока код
находится в draft PR, публикация в viewer-ветку не включена.
